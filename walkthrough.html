What problem is this for?

Companies often say “we approved that AI model” — but they mean a name, not a specific version.

Later, nobody can answer simple questions:

  • Which exact version did we review?
  • What proof did we have at the time?
  • What internal testing stayed private?
  • What was allowed or blocked?
  • If the model changed, does the old approval still count?

Today the answer is usually scattered across email, chat, docs, and websites. That is hard to audit and easy to get wrong.

What QEV is (one sentence)

QEV builds a signed package around an important file or AI model version so you can later check it is still the same thing — and see the proof that went with the decision.

Think of it like a sealed envelope for a decision: what was reviewed, what evidence was included, what was kept private, and what the final call was — all tied to one exact version.

The flow (big picture)

1. Start with a file or AI model
2. Lock in the exact version
3. Attach public proof (docs, supplier info)
4. Attach private notes if needed (encrypted)
5. Record the decision (for example: reject or sandbox only)
6. Save a signed package you can share and re-check later

What it can and cannot prove

It can help show…

  • The package still matches what was signed
  • The signature checks out
  • If something inside was changed
  • If private notes are included but locked
  • That a new version is not the same as the old approved one

It does not claim…

  • That a model is safe or good
  • That a model’s public description is true
  • That this is ready for big-company production use
  • That a lawyer would treat it as a notary seal
  • That an outside security firm audited it

Part 1 — click along (Sunline)

1

Open the demo

Go to the live demo. Look for a note that work stays in your browser.

2

Load the Sunline sample

Use the built-in sample (or drop in your own zip file). You should see a normal project: pages, scripts, folders — nothing “special” yet.

Say: “This is just a regular set of files.”
3

Look at what is included

Browse the file list. The point is simple: QEV tracks the real contents, not a vague product name.

4

Build the package

Create the QEV dossier and download it. That file is the portable record (a .qevpack).

5

Check the package

Open verify / simple view. Walk the rows slowly:

  • Signature — did the seal check out?
  • Integrity — is the content still the same?
  • Private evidence — are locked notes present?
These are separate checks. One “green light” is not enough in real life.
6

Break it on purpose

Use the tamper demo. One changed file should fail the check. That failure is the feature.

7

Optional: revoked issuer

Sometimes content is still intact, but you no longer trust who signed it. QEV can show that difference instead of hiding it.

Part 2 — AI model intake (why this matters for business)

1

Switch the story

“Same packaging idea — now for outside AI models your team wants to use.”
2

Tiny GPT-2 → rejected

Lock the exact version. Public proof is incomplete. Decision: rejected.

This is not “the model is evil.” It means: not enough recorded proof under the policy.
3

SmolLM2 → sandbox only

Better documentation — still not full production approval. Decision: sandbox only (limited use).

Real orgs need middle outcomes, not only yes/no.
4

Private testing stays private

Internal notes can be sealed inside the package. Outsiders can see that private evidence exists without reading it.

5

New version = new review

If the model version changes, yesterday’s approval does not silently transfer. The old package still matches the old version. The new version needs its own decision.

This is the core business value in one sentence.

Words you will see (decoded)

  • Dossier / package — the signed record you download
  • Revision / version pin — the exact model or build you reviewed
  • Integrity — “the bits still match”
  • Signature — “the seal checks with the expected key”
  • Revoked — “we no longer trust that signer”
  • Sandbox only — limited / non-production use
  • Proof of concept — working demo, not finished production software

A 5-minute path (if you are short on time)

  1. Explain the “name is not a version” problem (20 seconds)
  2. Sunline: load → build → verify → tamper (~90 seconds)
  3. Models: rejected vs sandbox only + private notes + new version rule (~2 minutes)
  4. Ask: does your team already struggle with outside AI model approvals? (30 seconds)

If yes, talk pilot next steps. If no, leave the links — do not force it.

Who this is for

  • Teams that pull open models from the internet
  • Security or risk people who must reconstruct decisions later
  • Groups that keep eval notes private but still need a clear record
  • Research and SBIR conversations about dual-use tooling

It does not need to replace your model host or registry. It aims to make the approval record portable and checkable.
